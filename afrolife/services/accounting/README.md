# AfroLife Accounting service

Accounting is a separately deployable TypeScript/Express/PostgreSQL service. It owns its entity hierarchy, accounting memberships, chart of accounts, periods, journals, audit trail, and consolidation totals. AfroLife's core database is not used for accounting records.

## Run standalone

Create a PostgreSQL database and a restricted runtime role that does not own the service tables and does not have `BYPASSRLS`. Create the role before the first migration; the migrator grants permissions but does not create database roles. Set:

- `ACCOUNTING_DATABASE_URL` to the restricted runtime connection.
- `ACCOUNTING_MIGRATION_DATABASE_URL` to a separate migration-owner connection used only by the controlled migration job; do not provide it to the running service.
- `ACCOUNTING_RUNTIME_DB_ROLE` to the runtime SQL role name in the migration job only.
- `ACCOUNTING_AUTH_MODE=local` and `ACCOUNTING_JWT_SECRET` to a random secret of at least 32 characters.
- `ACCOUNTING_INGEST_SECRETS` to a JSON object mapping each source service key to its own random secret of at least 32 characters. `ACCOUNTING_INGEST_SECRET` is supported as a single-key fallback for local development only.

From `afrolife/`, run `npm run migrate:accounting` during local development and `npm run start:accounting` to start locally. In production, build the image and apply migrations in a controlled release job with `npm run migrate:accounting:apply`, injecting the migration-only environment into that job. On first local-auth deployment, call `POST /api/v1/accounting/auth/bootstrap` once with `{ "email", "name", "password" }`; require a password of at least 12 characters. This creates the initial platform administrator and returns a bearer token. The bootstrap endpoint permanently closes after the first user exists. An administrator can create additional local users at `POST /api/v1/accounting/users`.

The service serves its standalone web workspace at `/` and listens on port 3300 by default. `/healthz` reports database connectivity. The first implementation exposes entity hierarchy and membership management, chart-of-account management with a reviewed starter template, accounting periods, double-entry journal submission and maker-checker decisions, book dashboard totals, a 12-month entity-scoped posted-journal/volume trend, and read-only parent consolidation totals. Dashboard and reports remain restricted to the caller's Accounting entity memberships.

## Local integrated development

For local development only, `npm run db:accounting:local:setup` provisions a separate `afrolife_accounting_local` database with a restricted runtime role, writes local-only gateway credentials to `%LOCALAPPDATA%\AfroLife\afrolife.env`, and applies the Accounting migrations. The setup refuses to overwrite an existing unmatched role or database. Start the gateway-mode Accounting service on loopback port 3301 with `npm run start:accounting:local`, then restart the AfroLife core API so it loads `ACCOUNTING_SERVICE_URL` and the matching gateway secret from the local environment file. The main app exposes the integrated workspace to authorized roles at the Accounting mini-app; create the business entity and chart from that workspace. Do not use the local database or generated credentials in production.

## Connect AfroLife

Set `ACCOUNTING_AUTH_MODE=gateway`, `ACCOUNTING_GATEWAY_SECRET` (32+ random characters), `ACCOUNTING_DATABASE_URL`, and `ACCOUNTING_MIGRATION_DATABASE_URL` on the service. Set `ACCOUNTING_SERVICE_URL` and the matching `ACCOUNTING_GATEWAY_SECRET` on AfroLife core. Core exposes the service under `/accounting` and signs short-lived identity assertions; the accounting service still checks its own entity memberships. Use HTTPS outside localhost. Do not expose the gateway-mode service directly to browsers.

For production, run migrations as a controlled release job with `ACCOUNTING_MIGRATION_DATABASE_URL` and `ACCOUNTING_RUNTIME_DB_ROLE`; create the restricted runtime role before the job, and do not give the migration-owner credential to the running Accounting service. Build the image once, then run `npm run migrate:accounting:apply` in the controlled job using the migration-only environment. The app container needs only the restricted `ACCOUNTING_DATABASE_URL`, gateway auth, and ingest secrets. Keep the Accounting listener private behind the approved HTTPS gateway. In gateway mode, provision Accounting entity memberships for verified AfroLife user UUIDs; do not initialize standalone local-auth users or switch auth modes on an existing database without an identity mapping plan. Example split configurations are `deploy/accounting-service.env.example`, `deploy/accounting-migration.env.example`, and `deploy/core-accounting.env.example`; they contain placeholders only and must be populated by the deployment secret manager. `npm run build:accounting` packages the SQL migrations; apply migrations before starting a release.

The accepted local Accounting sandbox is synthetic QA only. Its credentials, local database, entity, chart, event mappings, and posted QA journals must not be copied into production. Earlier `afrolife_test_accounting_*` databases were disposable test environments and were removed; they are not production migration sources or opening-balance evidence. Production still requires an approved legal entity, reviewed chart of accounts and source-account mappings, finance-approved opening balances, a backup/restore rehearsal, and staging evidence before live event delivery is enabled.

Integrated deployments use the verified AfroLife user UUID as the service membership subject. Standalone deployments use local Accounting UUIDs. Do not switch authentication mode on an existing database without an explicit identity mapping plan. Core exposes the API at `/accounting` when `ACCOUNTING_SERVICE_URL` is configured. The Accounting & Finance mini-app uses the platform's shared service subscription workflow at the same ETB 1,000 monthly fee as other mini-apps; access for customer and property-owner accounts requires a confirmed, unexpired subscription. Corporate finance roles continue to use the internal company workspace with role-based access.

Deploy the subscriber-facing Accounting service as a separate service instance with its own PostgreSQL database, credentials, backups, and hostname. Keep the internal AfroLife company books on their own database and private service endpoint. Configure the core gateway with `ACCOUNTING_SERVICE_URL` and `ACCOUNTING_GATEWAY_SECRET` for internal books, plus `ACCOUNTING_SUBSCRIBER_SERVICE_URL` and a distinct `ACCOUNTING_SUBSCRIBER_GATEWAY_SECRET` for subscribers. Core routes corporate finance roles to the internal service and customer/property-owner roles with an active platform subscription to the subscriber service. The two instances may use this image, but must not share a database, migration credentials, gateway secret, or subscriber data. Apply the Accounting migrations to each database independently. Subscriber root books can be self-created after subscription; the subscriber is assigned only entity-admin access to the book they create and receives no platform-admin bypass. The legacy local-auth mode is for isolated QA or separately operated deployments and does not itself synchronize with AfroLife subscription status.

Other mini-apps keep their own service-specific financial workflows and ledgers, such as rent reconciliation, commissions, MFI journals, and Edir/Insurance ledgers. These do not require opening the dedicated Accounting & Finance mini-app. The dedicated mini-app provides the full entity books, double-entry general ledger, journal review, accounting documents, budgets, bank reconciliation, tax workpapers, and reports. Shared global platform features, including the workspace shell, subscriptions, marketplace, privacy, and security, remain in the AfroLife platform rather than being duplicated inside the accounting service. The internal event-ingestion endpoint is service-authenticated and is not a user-facing accounting module.

## Financial event integration contract

Source services send finalized events to `POST /api/v1/accounting/internal/events` using `x-accounting-source`, `x-accounting-timestamp` (Unix milliseconds), and an HMAC-SHA256 `x-accounting-signature`. Each source should have its own secret in `ACCOUNTING_INGEST_SECRETS`. Sign `source + newline + timestamp + newline + method + newline + full request path + newline + SHA256(JSON body)`. The body contains `source_event_id`, `source_entity_id`, entry date/reference/description, balanced source-account lines, and source maker/checker IDs plus the checker reason. Configure the entity and every source-account mapping before events can post. The receiver verifies distinct maker/checker identities, maps to the entity chart, posts atomically, and deduplicates retries by source/event ID. Identical retries return the existing journal; payload mismatches return 409. Missing mappings fail closed for finance review.

## Entity books and reports

Every Accounting entity has its own chart of accounts, accounting periods, journals, balances, mappings, and audit trail. Journal lines and accounts have composite entity-safe database constraints; journal debits and credits are checked in integer cents by the API and again by the database before submission. Journal IDs and idempotency keys are unique, and each entity's source reference is also unique so a second transaction cannot silently reuse the same reference. Concurrent retries serialize on the idempotency key; source references also serialize before posting. Source event IDs are unique per source, making retries return the original journal. The API provides trial balance, income statement, balance sheet, and general ledger reports under `/entities/:entityId/reports/:report`; report calculations preserve integer-cent precision, and date-filtered general-ledger balances include pre-range opening activity. Document approval, document-payment review, budget approval, tax-filing transitions, bank-statement reconciliation, and period-close approval require an actor distinct from the maker/importer/requester. Period closing is a two-step request and independent approval, each with a recorded reason; a period close request serializes against journal submission. Parent users receive consolidated totals only unless they also have direct membership in each child book.

## AfroLife core rent feed

Core can publish an outbox event after a rent, deposit, or deposit-refund transaction has been reconciled by a different finance user. The source entity is the AfroLife property UUID; map that property UUID to its Accounting property-owner/landlord entity, then map source accounts `cash`, `rental_revenue`, and `tenant_deposit_liability` to that entity's approved chart. Configure `ACCOUNTING_SERVICE_URL` and the same `ACCOUNTING_INGEST_SECRET` as the `afrolife_core` key in the accounting service's `ACCOUNTING_INGEST_SECRETS`. Apply core migration 072. Core delivers with retries, idempotent source event IDs, and marks events dead after 12 failed attempts for operator review. Existing reconciliations are not backfilled automatically.

Agency contract activation, commission accruals, commission and holdback payouts, dispute refunds, Property vendor invoices/payments, approved MFI loan disbursements, savings transactions, repayments, write-offs and four-eyes reversals, Edir financial transactions, and approved Insurance journals also publish transactional outbox events. Property maintenance vendor invoices accrue Maintenance Expense against Accounts Payable after Finance entry and independent approval; a separate payment evidence/reconciliation clears the payable against Cash. Map source accounts `maintenance_expense`, `accounts_payable`, and `cash` for each property source entity to the confirmed property-owner entity and chart. Vendor IDs and invoice references remain in the Property subledger and Accounting source references; confirm vendor-level reconciliation in both systems. Property currently supports full invoice settlement; partial payments, credit notes, withholding/VAT, and vendor bank reconciliation remain future workflows. Agency entries use the agent UUID as the source entity and source account codes `Cash`, `Service Revenue`, `Guarantee Liability`, `Commission Expense`, `Commission Payable`, `Commission Held Payable`, and `Refunds` as applicable; configure and review their mapping to each agent's actual legal entity and approved chart. MFI savings and repayment requests use an independent finance approval before posting; approval writes the Accounting outbox event atomically with the journal. Apply the corresponding Edir and Insurance service migrations before enabling their publishers. Configure each source entity and every source account code in Accounting first. The Insurance service uses the same `ACCOUNTING_SERVICE_URL` and `ACCOUNTING_INGEST_SECRET` settings as core and sends with source name `afrolife_core`; its outbox is stored in the dedicated Insurance database. These feeds only cover new approved postings and do not backfill historical journals. Synthetic MFI connector examples are in `test/fixtures/accounting-source-events.json`. Workforce worker rates and Staffing offers/matches remain non-financial records until contracts, accepted work evidence, client receivables, and worker payment workflows are implemented; they publish no accounting events. Marketplace has an isolated sandbox order and simulated-payment path; it does not create accounting events or represent real checkout.

For Agency contract invoices, the signed payment webhook stores provider evidence but does not post a ledger entry or activate a contract. A Finance user must record that provider payment against the invoice (matching the verified amount and reference), then a different authorized finance user must reconcile it. Contract revenue, guarantee liability, commission accrual, and the Accounting outbox entries are then created atomically. The Accounting service therefore receives finalized and independently checked facts rather than raw webhook claims.

If delivery stops on a missing mapping, add or correct the entity/account mapping, then retry the dead event. Finance can inspect and retry core outbox events in the Accounting workspace. Edir and Insurance expose organization-scoped `accounting-event-outbox/status` and `accounting-event-outbox/:id/retry` routes on their finance APIs. Events stay in their originating service database until delivery succeeds or they are explicitly retried.

## Current implementation boundary

This remains a deployable accounting foundation, not a complete port of every ZIP workflow. The basic invoice/bill, contact, and tax workpaper workflows remain partial; BI comparisons/exports and production checkout remain unimplemented. Optional local tax and subscription mock providers require `ACCOUNTING_TAX_PROVIDER_MODE=mock` or `ACCOUNTING_BILLING_PROVIDER_MODE=mock`; they are disabled in production and explicitly mark results as simulations. They never contact a tax authority or collect money. Marketplace sandbox checkout requires `MARKETPLACE_PAYMENT_MODE=mock` and is also disabled in production. Tax submission through the real workflow requires an authority reference but does not call an authority service. Subscription trials are single-use 30-day records; paid activation and package changes require an authenticated billing-provider integration. Review source mappings before enabling delivery; no source feed backfills history. The archive's React/tRPC/MySQL code was not copied because it depends on a missing scaffold and its company ownership model cannot enforce AfroLife entity hierarchy or accounting controls.
